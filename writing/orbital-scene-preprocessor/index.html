307ms on a 2-core box: squeezing YOLOv8n onto a satellite's budget

Nobody assigned me this. I got curious about one specific question: how much of a satellite's imagery does it actually need to send down if it can decide what's in it before it transmits anything. The constraint I set for myself was simple to state and annoying to hit: run object detection on satellite imagery, on hardware you could actually fly — 2 cores, 4GB of RAM — fast enough to keep up with a pass window, inside a 400ms latency budget. Not a GPU. Not a dev laptop pretending to be the target.

The naive version — a stock YOLOv8n in full precision — wasn't close. On the same 2-core/4GB profile, FP32 landed around 560ms p99, already over budget before accounting for any variance under load. The 1.83x speedup from quantization is what actually closed that gap, not some other optimization layered on top of it.

Why the bottleneck wasn't the model architecture

It's tempting to go reach for a smaller architecture when you miss a latency budget. I didn't, mostly because the accuracy I needed came from the 6-band input — this isn't RGB, it's multispectral, and dropping bands was a worse trade than almost anything else I tried. So the lever I had left was quantization: INT8 instead of FP32, run through ONNX Runtime.

INT8 quantization is a tax you pay in accuracy to buy back latency and memory, and the exchange rate is not obvious until you actually measure it on your own model and your own data — generic quantization benchmarks don't transfer. On this model, the tax came out to 0.9 points of mAP@0.5. In exchange: the model got 3.43x smaller and 1.83x faster. I used static post-training quantization through ONNX Runtime, calibrated on a few hundred representative frames pulled from the actual target domain rather than a generic dataset — calibrating on the wrong distribution is the fastest way to quietly tank accuracy and not notice until you're already committed to the quantized weights. The detection head's final layers stayed FP16; quantizing those to INT8 cost disproportionately more accuracy on small objects than it bought in latency, so that was the one place I left precision on the table on purpose.

That got me to 307.65ms p99, against the 400ms budget. Quantization did almost all of that work by itself — I didn't need operator fusion or batching tricks on top of it, which honestly surprised me going in.

The other half: deciding what's even worth sending down

A detection on an edge device is useless if the downlink can't carry it, and satellite downlink is the scarcest resource in the whole pipeline — scarcer than compute, by a lot. So the preprocessor doesn't just detect; it decides what's worth transmitting. Detections get serialized into protobuf briefs, and I used SGP4 propagation to know in advance which pass windows actually matter, so the system isn't burning compute or bandwidth outside the window it needs to care about.

End to end, that cut payload size 1,484x compared to sending raw imagery down, at equal detection accuracy — because you're no longer sending the imagery, you're sending the conclusion.

What actually mattered, in order

1. The 6-band input was non-negotiable, which meant the entire quantization strategy had to work around preserving it rather than trading it away.

2. Static INT8 quantization bought almost the entire latency win, for a fixed, known accuracy cost — not a vague one.

3. SGP4 windowing turned "always-on inference" into "inference exactly when it's needed," which is a bigger bandwidth win than anything you can do to the model itself.

What I'd try next, if I kept going: mixed precision per-band instead of a uniform INT8 pass across all six — some bands almost certainly carry more detection-relevant signal than others, and treating them identically in the quantization pass is probably leaving latency on the table I haven't claimed yet.
