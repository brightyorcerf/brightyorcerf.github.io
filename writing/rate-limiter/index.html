When Redis goes away

Most posts about distributed token buckets say that concurrent requests break them. I wanted to watch it happen before I believed it, and then fix it in a way I could defend. The setup: Express middleware on Node.js, bucket state in Redis, token bucket as the algorithm.

The read-write gap

The bug isn't in the bucket math. It's in the gap between reading the token count and writing the decremented count back. On one process that gap barely matters. With several instances sharing a bucket, it becomes a real window: two requests read the same count, both decide they're allowed, and both decrement. A request that should have been denied gets through.

A lock in the application layer only moves the race into whatever implements the lock, and adds a slower part that can fail. Instead, I moved the whole read-decide-write sequence into Redis as a Lua script. Redis runs a script as a single operation, so nothing can interleave and the gap no longer exists.

The script reads the last-refill timestamp and the token count, works out how many tokens have regenerated using redis.call('TIME') (Redis's clock, not the caller's), applies the refill, decides, and writes the new state. Keys get a TTL slightly longer than a full refill, so idle buckets expire instead of piling up.

The middleware added 0.4ms per request: one round trip to Redis plus the script.

When Redis isn't there

A rate limiter that hard-fails when Redis is unreachable takes your API down harder than the traffic spike it was meant to absorb.

So every check races a 250ms timeout against Redis. If Redis answers first, the request gets the real, atomic decision. If the timeout wins, the middleware falls back to a token count kept in that instance's own memory, refilled on the same schedule but not shared between instances. With N instances, the effective limit during an outage can reach N times the configured one. I accept that on purpose: a looser limit is better than depending on the thing that just stopped responding. The fallback decision itself takes 1–2ms.

Allowed and denied requests are counted separately on both paths. Without that, a Redis outage and a traffic spike look identical on a dashboard.

What I'd keep

  • Put atomicity next to the shared state. Once the logic lived in a Lua script, I stopped thinking about locks.
  • Design the failure path on purpose, benchmark it, and give it its own metrics.
  • The timeout matters more than it looks. I underestimated the 250ms number until I load-tested the tail. For every request near Redis's p99, it decides whether you get a slow correct answer or a fast approximate one.

If you've built a fallback for a distributed limiter and handled the outage case differently, email me.
