Five ways my benchmarks lied to me

I spent a few weeks benchmarking two things: five parallel kernels in C with OpenMP, and seven concurrent data structures in Java, lock-based and lock-free, timed from 1 to 16 threads. Both ran on the same 4-core i5-7500 under macOS. The Java side alone is 1,890 timed runs.

None of the bugs below crashed anything or printed an error. Each one produced numbers that looked reasonable, sometimes better than reasonable, and each would have gone into the report if I hadn't gotten suspicious. That's the part worth writing down.

1. I was benchmarking the clock

The Java harness runs each structure for a fixed time and counts operations. The first version checked the deadline after every operation:

// roughly what the first version did
while (System.nanoTime() < deadline) {
    doOneOperation();
    count++;
}

Every fast structure hit the same ceiling, about 29 million operations per second, whatever the thread count. A read-only peek on a stack should scale with cores, and it sat flat at 29 MOPS.

So I timed the clock on its own. On macOS, HotSpot keeps nanoTime() monotonic with a compare-and-swap on one shared word, so every call from every thread fights over the same cache line. One thread got about 30 million calls per second, and four threads got 26 million between them. My benchmark had found the throughput of System.nanoTime().

The fix is to look at the clock less often:

while (System.nanoTime() < dl) {
    for (int j = 0; j < CHECK_EVERY; j++) {   // CHECK_EVERY = 64
        int e = w[i++ & MASK], k = e >>> 2;
        switch (e & 3) {
            case 0: ds.read(k); break;
            case 1: ds.insert(k); break;
            default: ds.delete(k);
        }
    }
    c += CHECK_EVERY;
}

peek went from a flat 29 MOPS to over 1,400.

2. The garbage collector was keeping my queues alive

Next, the two linked queues (a two-lock queue and Michael-Scott) started overshooting their 2-second runs by up to 0.8 seconds. GC logs showed 125 to 160 ms pauses and a live heap growing from 95 MB to 290 MB. A queue that keeps half its operations as dequeues shouldn't grow.

It wasn't growing. Its history was being kept alive. When you dequeue from a linked queue, the old sentinel node becomes garbage, but it still points at the next node. If that dead sentinel has survived long enough to be promoted to the old generation, a young collection treats its next pointer as a root. The node it points to survives and gets copied, along with everything after it. Each young GC was copying the entire chain of dequeued nodes.

The fix is one line: point the dead node at itself, so it holds nothing alive.

} else if (head.compareAndSet(first, next)) {
    first.next.set(first);   // self-link: a stale reader sees this and fails its head check
    return next.value;
}

I found out afterwards that java.util.concurrent.ConcurrentLinkedQueue does the same thing, for the same reason.

3. Sleep stops the clock

A full sweep takes about an hour, long enough for the Mac to fall asleep partway through. System.nanoTime() stops while macOS sleeps, so a run that straddles a sleep comes back looking short and slow, which reads as a performance result and not as a broken run.

caffeinate -i wasn't enough to prevent it. Now the sweep runs under caffeinate -dims on AC power, and before any results are accepted, a script rejects every raw file with an elapsed time above 2.05 seconds.

4. OpenMP made my loop 5.5x slower

This one was in the C kernels: squaring a matrix whose entries are all −1, 0 or 1. The hot loop is just c[j] += b[j] over a row. With Apple clang, that loop written inside an omp parallel for ran in 0.48 s at N = 1024. The same loop in a build without OpenMP ran in 0.087 s, 5.5 times faster, on one thread in both cases.

The disassembly explained it. The sequential build had 108 vpaddd instructions in the kernel and the OpenMP build had 36. OpenMP moves the body of a parallel region into a separate function, and in that function the loop was vectorised but barely unrolled.

The fix is to give the compiler a small function with no aliasing questions, and to stop it inlining that function back into the parallel region:

NOINLINE static void row_add(int32_t *restrict c,
                             const int32_t *restrict b, int n)
{
    for (int j = 0; j < n; j++) c[j] += b[j];
}

After that, the OpenMP binary on one thread is within 2% of the sequential binary on all five problems.

This bug flatters you. Speedup is time at one thread divided by time at t threads, so a slow one-thread baseline makes every speedup look better. My speedup plots would have improved while the code got slower.

5. zsh ran the default algorithm six times

The sweep script passed options through a variable:

args="--algo bmm --block 4"
prog $args

Bash splits $args into four arguments. zsh doesn't, so the program received one argument, "--algo bmm --block 4", matched no option, and quietly ran the default unblocked kernel. I got a table of six "block sizes" that were all the same algorithm. They were, unsurprisingly, identical.

Now any unrecognised option is a hard error, with a hint when the argument contains a space. I'd rather the program refuse to run than report a confident wrong number.

What was left once the numbers were honest

With all five fixed, the stacks showed something I didn't expect. Under a write-heavy load (half pushes, half pops), the lock-free Treiber stack falls from 51 MOPS at one thread to 9.6 at four. Every thread fights over the same top pointer, and failed compare-and-swaps add more traffic to that one contended cache line. The plain lock-based stack holds 19.5, twice as much. The elimination stack is the outlier: pushes and pops that collide cancel each other in a side array and never touch top, which gives it 3.3 to 4.4 times Treiber's throughput from 8 to 16 threads.

What I do differently now

Each of these produced a believable number, so "does the output look reasonable" was never going to catch them. What caught them was cross-checking things that should agree: the clock's own throughput against the benchmark's, the requested run time against the measured one, the OpenMP binary on one thread against the sequential binary, and six configurations that should have differed and didn't. The C harness now prints a checksum on every run and refuses to report a time for a result it couldn't verify against the sequential version.

Everything is in parallel-universe: the code, every raw run, the gnuplot scripts and both reports. If you rerun it on Linux, I'd like to know whether the nanoTime ceiling disappears. Email me.
